# Token and Scaling Policy

This project keeps the representative respondent layer separate from report/dashboard summarization.

The original product design is preserved: a 10,000-person representative synthetic panel may produce 10,000 respondent-level choices. In the intended product mode, those choices can be generated by LLM short interviews for every selected persona.

## Core rule

Do not place full `personas_enriched.jsonl`, `choice_results.jsonl`, raw LLM interview text, or other row-level artifacts into a single LLM prompt or Markdown report.

Use JSON/JSONL artifacts as storage and compute surfaces. Use Markdown, HTML dashboards, or LLM summaries only on aggregated outputs, sampled examples, or bounded slices.

## Recommended tiers

| Tier | Typical size | Method | LLM use |
|---|---:|---|---|
| Representative choice layer | 10,000+ | weighted personas, isolated short choice task, weighted aggregation | allowed for all personas in `llm_short_all`; prompt must stay short |
| Medium explanation | ~1,000 | stratified or uncertainty-focused respondents | optional richer LLM explanation |
| Deep cases | ~100 | high-value or uncertain personas, qualitative explanation | allowed with isolation controls |
| Deterministic baseline | any size | rule-based choice, smoke tests, comparison | none |

## Pipeline cost boundary

The current deterministic pipeline stages do not call an LLM per persona:

```text
country pack
→ seed cells
→ IPF/raking
→ persona skeletons
→ soft traits
→ coherence validation
→ product normalization
→ rule-based baseline choice
→ bootstrap
→ concise report / dashboard data
```

The intended LLM interview mode adds this branch:

```text
personas_enriched.jsonl
+ normalized_choice_scenario.json
→ one isolated short prompt per persona
→ LLM choice_results.jsonl
→ weighted aggregation
→ bootstrap / dashboard / report
```

The cost control is not reducing choice coverage. The cost control is keeping each persona prompt short and avoiding second-stage summarization over all raw rows.

## Report and dashboard boundary

`market_report.md` is a compact text surface. It is not meant to display the full study.

A richer HTML dashboard should read compact artifacts such as:

- `market_report.json`
- `choice_model_audit.json` or `llm_choice_interview_audit.json`
- `choice_interview_validation.json`
- `bootstrap_intervals.json`
- `pipeline_artifact_validation.json`
- aggregated reason-code tables
- sampled examples, not all rows

## LLM interview policy

If LLM short interviews are used for all personas:

1. Every selected representative persona may receive one short isolated choice prompt.
2. Never show a respondent other respondents' answers.
3. Never show aggregate shares, quotas, or target proportions.
4. Keep prompt inputs compact: hard traits, key soft traits, optional short story, normalized product scenario.
5. Store each row-level response in JSONL.
6. Validate each response with `validate_choice_interviews.py`.
7. Aggregate with deterministic scripts using `population_weight`.
8. Summarize aggregated artifacts, not full row text.
9. Record prompt version, model, seed/temperature, and isolation controls.

## Failure modes to avoid

Do not run this pattern:

```text
10,000 personas
→ 10,000 long LLM interviews
→ paste all answers into one Markdown or LLM summary
```

That pattern is expensive, hard to audit, and likely to compress variance during summarization.

Use one of these patterns instead:

```text
10,000 personas
→ 10,000 short isolated LLM choice interviews
→ validated JSONL choices
→ weighted aggregation
→ dashboard JSON / concise report
```

or, for development:

```text
10,000 personas
→ deterministic baseline choices
→ smoke-test aggregation
→ compare against LLM interview mode when available
```
